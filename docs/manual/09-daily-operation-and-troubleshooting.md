# 09. 日常運用とトラブルシューティング

## 日常の確認順序

1. Workspace の「概要」で、人間確認、未処理 Drift、承認済み・未反映、反映確認済みの件数を見ます。
2. 「次に確認すること」から未評価の提案を開き、本文、差分、根拠を確認します。
3. プロジェクトの「ずれの検知」で、未処理と対応中の指摘を処理します。
4. 承認後は「反映状況」で Draft PR をレビューし、GitHub で人間がマージします。
5. 「表示を更新」し、マージ後の確認 commit と検証済み表示を確認します。
6. 判断の経緯は「判断記録」、運用操作は「監査ログ」で追跡します。

## 状態を混同しない

| 確認対象 | 完了の目安 |
|---|---|
| 提案 | Version が提案中で、本文・差分・根拠を閲覧できる |
| 承認 | Version が承認済みで、現行 Version と判断記録が更新される |
| 生成 | 生成ジョブの完了後に生成物と Draft PR を実画面で確認できる |
| マージ | GitHub の PR が default branch にマージ済み |
| 反映検証 | RuleBranch の確認 commit がマージ後 commit と一致し、検証済み |
| Drift 解決 | 対象指摘が解決。GitHub 反映完了は別途確認する |

## よくある問題

### 画面が読み込み中のまま

少し待ってからブラウザを再読み込みします。対象 Workspace と Project が正しいか、リポジトリが active かを確認します。続く場合は監査ログの request ID と発生時刻を記録して管理者へ渡します。

### job が queued または running のまま

同じ操作を連打せず、画面の更新機能を使います。長時間変わらない場合は job ID、種類、開始時刻、Project、Repository を記録し、Worker と Cloud Tasks の運用ログを確認します。failed または dead は完了扱いにしません。

### Draft PR が表示されない

生成ジョブの状態だけで判断せず、「表示を更新」後のリポジトリカードを確認します。GitHub App が対象リポジトリへ接続されているか、生成対象の承認済みルールがあるかも確認します。差分がない場合は新しい PR が作られないことがあります。

### マージしたのに検証済みにならない

GitHub 上のマージ commit と RuleBranch の確認 commit を照合します。検証待ちなら少し待って更新し、不一致なら対象 path と生成物を確認します。必要に応じて再生成し、修復用 Draft PR を人間がレビューしてマージします。

### 権限がなく操作できない

画面左下の「現在の権限」を確認します。閲覧、指摘の判断、承認、生成、メンバー管理、監査ログでは必要ロールが異なります。別ユーザーのロールを推測せず、オーナーまたは管理者に確認します。

### ログイン後に目的の画面へ戻らない

保護された URL からログインした場合は、ログイン後に元の相対 path と query へ戻る設計です。戻らない場合は目的の URL、ログイン開始時刻、遷移先を記録します。公開 source に対応する実装はありますが、利用中の環境では実際の遷移を確認してください。

## 問い合わせ時に残す情報

- 発生日時とタイムゾーン
- Workspace、Project、Repository、rule または Version の名前
- 画面に表示された状態、エラーメッセージ
- job ID、request ID、commit SHA、PR 番号のうち表示されたもの
- 再現手順と、最後に成功した操作

Cookie、OAuth state、access token、秘密鍵はスクリーンショットや問い合わせ文に含めません。
