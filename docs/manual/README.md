# RuleBranch WEB マニュアル

このマニュアルは、RuleBranch で GitHub リポジトリと開発ルールを結び付け、コードとのずれを確認し、改定案をレビューして GitHub へ反映する人向けです。掲載画面は 2026-10-14 時点の画面構成を基にしています。

## はじめる前に

- GitHub でログインできること
- 対象リポジトリに RuleBranch GitHub App をインストールできること
- Project 作成や承認を行う場合は、その Workspace で必要な権限があること

掲載画面は個人 Workspace のオーナーで確認したものです。個人 Workspace ではオーナーが全操作を行います。組織 Workspace 専用の組織ルール、ルール関係、招待、複数ロールの権限制御は、公開されている画面実装と設計に基づいて説明しています。

## 最短の利用手順

1. GitHub でログインし、GitHub App と Project を設定します。
2. ルールを作成するか、Drift から改定提案を作ります。
3. Version の本文、差分、根拠を確認して承認します。
4. 「反映状況」から Draft PR を作り、GitHub で人間が確認してマージします。
5. RuleBranch に戻り、マージ後の検証が「検証済み」になったことを確認します。

## 画面と操作の確認区分

本文では、次の区分を使います。

- **画面確認済み**: 2026-10-14 に表示し、必要に応じて操作結果まで確認した内容です。
- **安全確認でキャンセル**: 保存、承認、再生成などの確認画面まで開き、共有データを変更する直前でキャンセルした内容です。
- **ソース確認のみ**: 組織 Workspace や別ロールが必要、または削除・解除など影響が大きいため、公開されている画面実装と設計で確認した内容です。

スクリーンショットは 2026-10-14 に取得した29枚です（1440 × 1000）。識別情報は、元の文字に依存しない不透明な固定パターンでマスクしています。画像は画面構成の例であり、現在のデプロイ状態や継続的な動作を証明するものではありません。

## 操作を理解するための重要な区別

RuleBranch では、次の状態はそれぞれ別です。

1. 解析・提案・生成ジョブが完了する
2. Rule Version が承認される
3. Draft PR が作成される
4. GitHub で人間が PR をマージする
5. マージ後の生成ファイルが検証済みになる

`完了` や `承認済` だけを見て GitHub への反映まで終わったと判断せず、最後に Project の「反映状況」を確認してください。


各章では、画面で確認した範囲と、公開 source から説明している範囲を区別します。固定 fixture、画面観測、実接続 E2E の違いは[デモと Evidence の読み方](../design/08-demo-and-evidence.md)も参照してください。
