# 既存のAI指示ファイルとの共存

RuleBranch は `AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` のうち、次の区間だけを更新します。区間外の手書きの指示やフロントマターは保持します。

```markdown
<!-- BEGIN RULEBRANCH MANAGED RULES -->
ここに承認済みルールが生成されます。
<!-- END RULEBRANCH MANAGED RULES -->
```

Repositoryの `compileTargets` で `agents-md`、`claude-md`、`copilot-instructions` を選んだ場合に、それぞれ上記のファイルを生成する。`rulebranch-rules` は共有ファイルとは別に、既定では `.rulebranch/rules/L1|L2|L3/*.md` と必要な場合の `_denied.md` を生成する。生成先ディレクトリはRepositoryの `rulesPath` で変更できる。

初回導入では既存ファイルの末尾へ管理区間を追加します。Draft PR で、既存の指示と生成されたルールに矛盾がないかを確認してからマージしてください。手書きの追記は管理区間の外側に置きます。

出力先を無効にしたときは管理区間だけを取り除き、手書きの部分を残します。管理区間しかないファイルは削除対象になります。

以前の RuleBranch が生成した、区間マーカーのない `Generated by RuleBranch.` 形式のファイルは、現在参照しているbaseline（開いているDraft PR、なければ最新のmerged PR）の保存済み生成物とGit blob SHAが一致する場合に自動移行します。baselineがない、保存済みSHAがない、または手書き変更により一致しない場合は上書きせずcompile jobを失敗させます。既存の生成部分を上記の開始・終了マーカーで囲み、手書きの追記を区間外へ移してから再コンパイルしてください。

開始・終了マーカーの重複、片方だけの存在、順序の誤り、マーカーが単独行でない場合もcompile jobは失敗する。ファイルを修復してから再コンパイルする。GitHubから読み取ったblobの内容がそのSHAと一致しない場合も停止する。ファイルの読み取り後に公開元のdefault branchまたは既存Draft PRのheadが変わった場合は公開せず、新しいbranch内容で再実行する。

生成物の保存・マージ後の検証には、手書きの部分を含む実際のファイル内容とハッシュを使います。区間外を編集した後もファイル全体の不一致が表示される場合は、再コンパイルして新しい生成物を記録してください。

## 停止したcompile jobを復旧する

### 1. 修復するブランチを先に確認する

「反映状況」から対象RepositoryとPRを開き、GitHub側でもRuleBranchの未完了PRがあるか確認します。Firestoreにまだ記録されていないPRをWorkerが回収する場合もあるため、画面の記録だけで「PRなし」と判断しません。

| GitHub側の状態 | ファイルを修復するブランチ |
| --- | --- |
| RuleBranchのPRが開いている | そのPRのheadである `rulebranch/rules-update` |
| RuleBranchのPRが開いていない | Repositoryのdefault branch |

開いているPRを使うコンパイルは、そのheadのファイルを読みます。default branchだけを修復しても、PR側に不正なマーカーが残っていれば再び失敗します。PRがある場合、実際のbase/headが対象Repositoryの組み合わせであることも確認してください。

### 2. 手書きの内容を保護して修復する

対象ファイルの現在の内容とPR差分を退避し、開始・終了マーカーを単独行で1組だけ置きます。旧形式の生成部分だけを囲み、維持すべき手書き指示とフロントマターを区間外に移します。生成ルールの本文に予約済みのマーカー文字列を含めないでください。

修復を上表のブランチへcommit・pushします。default branchが保護されている場合は、通常の修復PRでレビュー・マージしてから再コンパイルします。SHA不一致を回避するためにFirestoreの保存済みハッシュを手動で書き換えたり、ファイル全体を削除して進めたりしないでください。

### 3. 再実行と完了確認

修復後、プロジェクトの「反映状況」から対象Repositoryの生成を再実行します。過去の `dead` jobはコードやファイルの修正だけでは再開しません。新しいcompile jobのIDと状態を確認してください。配送・Workerエラーの切り分けは [GCP構築手順](./gcp-deployment.md) を参照します。

新しいjobの `done`、PR差分での管理区間と手書き部分の保持を確認してから、人間がPRをマージします。その後、反映照合が `verified` であることを確認します。既にdefault branchの内容が期待値に一致し、開いているPRがない場合は、新しい差分やPRを作らず既存のmerged PRの検証記録を更新することもあります。

読み取り後にブランチheadが変わったことだけが停止理由なら、最新の差分を確認して再実行します。変更が競合している間に連続再実行しないでください。最初の配布全体の確認は [初回ルール配布](./first-rule-publication.md) を参照してください。
